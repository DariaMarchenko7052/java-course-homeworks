# MindZone

### Проблема
Сучасні таск-менеджери часто створюють візуальний хаос, відображаючи сотні різнокольорових завдань на одному екрані, що розсіює увагу та викликає відчуття тривоги. Користувачам складно фокусуватися на конкретній сфері життя (навчанню, роботі чи спорту), коли всі справи перемішані в один суцільний список.

### Рішення
Застосунок структурує завдання за допомогою тематичних секцій (папок) на головному екрані (наприклад: «Університет», «Спорт», «Робота»), що дозволяє бачити загальну картину дня без зайвого інформаційного шуму. Крім чіткого розподілу активностей, додаток підтримує систему дворівневих нотаток: користувач може створювати як загальні конспекти для всієї секції, так і окремі швидкі нотатки до кожного конкретного завдання всередині неї. Також відображується кількість задач по кожній секції, що допомагає проаналізувати свій день за допомоги виводу інфографіки.

### Цільовий користувач
Студенти, фрілансери та люди з високим рівнем щоденної багатозадачності, які прагнуть структурувати свій день, позбутися візуального шуму у списках справ та тримати важливі нотатки й завдання в одному організованому місці.

## Інженерні вимоги

### 1. Функціональні вимоги (User Stories)
* **Як користувач**, я хочу створювати тематичні секції (наприклад, "Навчання", "Спорт"), **щоб** розділяти свої завдання за сферами життя та уникати візуального хаосу.
* **Як користувач**, я хочу додавати завдання всередину конкретної секції, **щоб** вони не змішувалися з іншими справами на день.
* **Як користувач**, я хочу мати можливість додавати текстові нотатки до кожного конкретного завдання, **щоб** тримати необхідний контекст (посилання, ідеї) під рукою.

### 2. Вимірювані обмеження (Non-Functional Requirements)
1. **Performance (Продуктивність):** Час відповіді сервера (API) при створенні нового завдання чи отриманні списку завдань не повинен перевищувати **300 мс** (95 перцентиль).
2. **Security (Безпека):** Усі ендпоінти API повинні бути захищені за допомогою авторизації через JWT. Система має забезпечувати ізоляцію даних: спроба отримати доступ до завдань або секцій іншого користувача повинна повертати статус 403 Forbidden.
3. **Availability (Доступність):** Архітектура бекенду повинна бути спроєктована таким чином, щоб забезпечувати безперебійну роботу системи (uptime) на рівні **99.9%** на місяць.

### 3. Дизайн ключових ендпоінтів (API Contracts)

#### Ендпоінт 1: Створення нового завдання
* **Метод та URL:** POST /api/v1/sections/{sectionId}/tasks
* **Опис:** Створює нове завдання всередині вказаної секції.
* **Request Body (JSON):**

    {
      "title": "Написати звіт з практики",
      "note": "Використати дані з останньої лабораторної",
      "dueDate": "2026-05-25T18:00:00Z"
    }

* **Response (201 Created):**

    {
      "id": "task-uuid-8742",
      "sectionId": "section-uuid-112",
      "title": "Написати звіт з практики",
      "note": "Використати дані з останньої лабораторної",
      "status": "TODO",
      "createdAt": "2026-05-23T20:30:00Z"
    }

#### Ендпоінт 2: Отримання денної статистики (для інфографіки)
* **Метод та URL:** GET /api/v1/analytics/daily?date=2026-05-23
* **Опис:** Повертає статистику кількості завдань по секціях на вказану дату.
* **Request Body:** Немає
* **Response (200 OK):**

    {
      "date": "2026-05-23",
      "totalTasks": 12,
      "distribution": [
        {
          "sectionName": "Університет",
          "taskCount": 8
        },
        {
          "sectionName": "Спорт",
          "taskCount": 4
        }
      ]
    }

### 4. Тест-кейси

**Test Case 1: Успішне створення завдання у секції**
* **Given:** Користувач успішно авторизований у системі та має існуючу секцію "Робота" (ID: 112).
* **When:** Користувач відправляє валідний POST запит на ендпоінт /api/v1/sections/112/tasks із полем "title": "Відправити звіт".
* **Then:** Система зберігає завдання та повертає HTTP статус 201 Created разом із згенерованим id нового завдання.

**Test Case 2: Валідація порожньої назви завдання**
* **Given:** Користувач знаходиться на формі створення нового завдання.
* **When:** Користувач намагається створити завдання, відправляючи POST запит, де поле "title": "" (порожній рядок).
* **Then:** Система відхиляє запит, завдання не створюється, і сервер повертає HTTP статус 400 Bad Request із повідомленням про помилку валідації.

**Test Case 3: Перевірка ізоляції даних (Security)**
* **Given:** Користувач "А" має секцію з ID 999. Користувач "Б" успішно авторизований у системі та має власний валідний токен доступу.
* **When:** Користувач "Б" намагається відправити GET запит до чужої секції за адресою /api/v1/sections/999/tasks.
* **Then:** Сервер розпізнає невідповідність власника, блокує доступ і повертає HTTP статус 403 Forbidden (або 404 Not Found).
